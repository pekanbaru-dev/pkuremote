## ADDED Requirements

### Requirement: `proto/` is the single source of truth for the API contract

The API between the SvelteKit BFF and the Go service SHALL be defined exclusively in hand-written `.proto` files under `proto/`, managed by buf (`buf.yaml` at the proto root, `buf.gen.yaml` for codegen). Packages SHALL be versioned (`events.v1`, `auth.v1`); the contract SHALL cover the full event domain surface: event and category reads, registration booking/cancellation/lookup, admin event CRUD, attendee status, dashboard aggregates, attendee CSV export, banner upload, and `AuthService.GetMe`. No RPC SHALL exist in code without a corresponding `.proto` definition.

#### Scenario: A new RPC starts in the contract

- **WHEN** a developer adds a new API capability
- **THEN** the `.proto` file changes first, `buf generate` produces the Go and TypeScript stubs, and only then are handler and caller implemented against the generated types

#### Scenario: Contract completeness

- **WHEN** the BFF's server code is inspected after the migration
- **THEN** every event-domain data access goes through a generated client method that corresponds to a `.proto`-defined RPC

### Requirement: buf lint and breaking-change detection gate the contract

CI SHALL run `buf lint` on every change touching `proto/**` and `buf breaking` against the base branch, failing the pipeline on lint violations or backwards-incompatible contract changes. Intentional breaking changes require an explicit override recorded in the PR.

#### Scenario: A breaking contract change is caught

- **WHEN** a PR renames a field or changes a field number in an existing message
- **THEN** `buf breaking` fails CI and the change cannot merge without an explicit, recorded override

#### Scenario: Lint enforces style

- **WHEN** a `.proto` file violates buf's configured lint rules (naming, package versioning)
- **THEN** `buf lint` fails CI with the violation listed

### Requirement: Generated code is committed and regenerated by one command

`buf generate` SHALL emit connect-go stubs into `api/` and connect-es (TypeScript) stubs into `web/` at fixed, documented paths. Generated code SHALL be committed to the repository so neither app's build requires the buf toolchain. A single documented command SHALL regenerate both sides, and CI SHALL verify that committed generated code is in sync with the `.proto` sources.

#### Scenario: Builds do not require buf

- **WHEN** `pnpm build` runs in `web/` or `go build` runs in `api/` on a clean checkout
- **THEN** both succeed using the committed generated code, without invoking buf

#### Scenario: Drift between proto and generated code is caught

- **WHEN** a PR modifies a `.proto` file without regenerating
- **THEN** CI's regenerate-and-diff check fails, pointing at the stale generated files
